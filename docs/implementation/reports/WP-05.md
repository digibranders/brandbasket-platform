# WP-05: Account Erasure Ordering and Route Auth Report

## 1. What Changed
- **Account Erasure Ordering**:
  - Reordered the execution sequence in `apps/customer/src/platform/lib/account-erasure-run.ts` so that `eraseRows` executes under its database lock before `eraseWebsiteContent` (CMS deletion) is called.
  - If an account is restored during the 30-day window, `eraseRows` re-checks the closure status under lock, detects `restoredAt !== null`, and skips the erasure (`reason: "not-due"`). Because `eraseWebsiteContent` is called only after `eraseRows` successfully commits erasure, a restored account loses no CMS content (blog posts, authors, categories, media, tenants) and no database rows.
  - Updated `docs/account-erasure.md` documentation to describe the updated ordering (rows under lock first, then CMS website content, then files and videos).
- **Internal Route Unit Tests**:
  - Added the missing route test suite in `apps/customer/src/app/api/internal/erase-closed-accounts/route.test.ts`.
  - Tested HTTP 503 response when `ACCOUNT_ERASE_TOKEN` is unset or not configured.
  - Tested HTTP 401 response when the Authorization header is missing or contains an invalid Bearer token.
  - Tested HTTP 400 response when query parameters are invalid (e.g. `dryRun=2`, `limit=0`, `limit=101`, `limit=abc`).
  - Tested HTTP 200 response when valid credentials and parameters are supplied, verifying dispatch to `runAccountErasure` with parsed parameters (`limit`, `dryRun`) and `realErasureDeps()`.
- **Integration Test Coverage**:
  - Added comprehensive integration tests in `apps/customer/src/platform/lib/account-erasure.integration.test.ts`.
  - Probed race condition where a restore occurs between `findBlock` and `eraseRows`, verifying that `eraseRows` catches the restoration under lock, skips erasure, never calls `eraseWebsiteContent`, and leaves all customer database rows untouched.
  - Tested dry run mode (`dryRun: true`), confirming report contains `would-erase` and mutates neither database rows nor CMS content.
  - Tested limit enforcement (`limit: 1`) with multiple closures due, verifying that only the specified limit of accounts is erased while others remain untouched.
  - Tested route authentication (503 and 401) and dry-run execution end-to-end via POST requests.
