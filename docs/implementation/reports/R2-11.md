# R2-11: end to end journeys, axe sweep and keyboard pass

Branch `r2/11-e2e-journeys-2`, run against `origin/development` at the time of the run. Test code only: no application code was changed. Defects are in `R2-11-defects.md`.

## Result in one paragraph

347 tests ran in 7.5 minutes: 288 passed, 41 failed, 18 skipped. The 41 failures come from 12 distinct defects, and one more was seen while exploring (13 in the defects file). Every journey in the list runs at 1440, 768 and 390 except the data-changing steps, which run once at 1440 (the three viewports share the fixtures). There is no failure from the harness itself. The release gate "zero serious axe issues on real screens" is not met: 29 route and viewport pairs have a serious `color-contrast` violation, and no other axe rule fired. Modal dialogs in both apps let Tab leave the dialog.

## Keyboard pass

- Signed out `/login`, `/signup`, `/forgot-password`: Tab reaches the primary action, every stop shows a focus indicator, focus wraps and leaves the page: pass at all viewports.
- Signed in `/`, `/website`, `/requests`, `/billing`, `/settings/team`, and console `/`, `/clients`, `/payments`, `/privacy-requests`: every visible action in `main` is reached by Tab (controls with `tabindex="-1"` are excluded, which covers roving filter chips) and each stop shows focus: pass.
- Dialogs: open by keyboard, Tab twelve times, assert focus never leaves the dialog, Escape closes, focus returns to the trigger. Customer New request, customer Invite someone and console refund dialog fail the "focus stays in the dialog" step (D10). Measured on the Next dev server; the dev overlay button is excluded from the check.
- The focus indicator check is lenient (outline, box shadow or `:focus-visible`). It does not measure contrast of the ring.

## Environment and how to run again

Needs a customer app and a console running locally and a local Postgres with the platform roles. Do not point it at anything else: `fixtures.ts` refuses unless `DATABASE_URL_STAFF` ends in `/brandbasket_platform_r211`.

1. `pnpm install`, then `pnpm env:init` (random secrets, no real keys; files are gitignored). Delete them when done.
2. Shell only (never in a file): the r211 database URLs, then blank overrides `BREVO_API_KEY= RAZORPAY_KEY_ID= RAZORPAY_KEY_SECRET= RAZORPAY_WEBHOOK_SECRET= SOCIAL_AUTO_URL= SOCIAL_AUTO_KEY= CALCOM_API_KEY= CALCOM_WEBHOOK_SECRET= VERCEL_API_TOKEN= TURNSTILE_SECRET_KEY= BILLING_PROVIDER=fake EMAIL_CODE_BYPASS=false CLIENT_SITE_BASE_DOMAIN=sites.example.test APP_ORIGIN=http://localhost:3312 ADMIN_ORIGIN=http://console.brandbasket.localhost:3313`, and a random `ACCOUNT_CODE_SECRET` (the app refuses to send sign-up codes without one and `pnpm env:init` does not write it: `export ACCOUNT_CODE_SECRET=$(openssl rand -hex 32)`).
3. Confirm `psql "$DATABASE_URL_OWNER" -Atc "select current_database()"` prints `brandbasket_platform_r211`, then `pnpm db:migrate`. Do not run `pnpm db:roles`.
4. In `apps/customer`: `pnpm exec next dev -p 3312`. In `apps/admin`: `pnpm exec next dev -p 3313`.
5. In `apps/customer`, with the same shell environment: `pnpm exec playwright test -c playwright.r2.config.ts`. Useful filters: `--project=setup`, `--project=w390`, `--project=admin-w768`, `-g "Social-only"`. After the first run, add `--no-deps` to reuse the accounts.
6. Per run output: `apps/customer/e2e/.logs-r2/report.json` and `axe.jsonl`; sessions in `apps/customer/e2e/.auth-r2/`. Each full run signs up eight new accounts, clears `rate_limit_buckets` in the r211 database between sign-ups (the per-network limit would otherwise stop the setup), and creates one staff member. Only the r211 database is touched.

Two harness notes: the three viewport projects share the fixture accounts, so projects must run one after another (workers = 1, the default). Specs that change data are guarded to run at 1440 and each journey resets what it needs, so a re-run after a partial run is safe.

## Environment deviations to know about

- `pnpm env:init` wrote no `ACCOUNT_CODE_SECRET`; a random one was exported in the shell for the app processes. Without it, sign-up fails with "We could not load this page".
- `EMAIL_CODE_BYPASS` stayed `false`. The real code was read from the outbox row (the outbox keeps sign-up codes in full on a local origin).

## CI

Not added. The suite needs two running apps, local Postgres roles, a shell-only secret set and a serial 8 minute run; the existing CI job builds rather than serves. Run it with the commands above before a release. If CI is wanted later, the smallest stable piece is the signed out axe and keyboard specs plus the console `/login` spec, which need no accounts.
